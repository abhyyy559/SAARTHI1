### Bugs found and fixed (all were SILENT — no exception, no log)

**1. `tests/test_adv_rule_isolated.py` broke the whole suite.**
`from weathergpt.backend...` instead of `from backend...`. Collection error meant
`pytest` aborted entirely — 187 tests never ran. Fixed the import (+1 file).

**2. kv keys with `:` wrote to an NTFS alternate data stream (db.py).**
`mode_persistence._KEY = "mode:source_mode"` → `_json_kv_set` built the filename
`kv_mode:source_mode.json`. On Windows a `:` in a path is not a filename, it
starts an ADS: the write "succeeded" and even round-tripped in-process, but no
ordinary file appeared — invisible to listings, backups, git and OneDrive.
Added `_kv_filename()` (sanitise, stable, readable) + a legacy-name fallback
read so pre-fix rows still resolve. Also stopped `_json_kv_set` swallowing write
errors silently.

**3. `CACHE_FILE` was relative → the store location followed the cwd (config.py).**
Two divergent stores existed: `SAARTHI/store/` (8406-byte watcher state) and
`weathergpt/store/` (15871-byte). `run.py` and `start-saarthi.bat` both cd into
`weathergpt/`, but any other launch resolved to the repo root — so the mode, the
demo alert store and the ledger silently split in two. Anchored `CACHE_FILE` to
`BASE_DIR` (`Path(__file__).resolve().parent.parent`); an absolute CACHE_FILE is
still honoured. Verified identical from both cwds.

**4. The mode restore was DEAD CODE (main.py).** ← the one that made the demo look broken
`_restore_mode` was registered with `@app.on_event("startup")`, but the app passes
a custom `lifespan=`. Starlette's merged lifespan does NOT include `_DefaultLifespan`
(the thing that invokes on_startup handlers), so the handler was never called —
proved with a spy: `_restore_mode invoked: []`. Result: every restart re-read
`.env` (`DEMO_MODE=false`) → came up hybrid → `/api/demo/*` 403'd → the demo panel
and coverage dashboard polled into a wall of 403s. Moved the restore into
`lifespan()`, deleted the dead handler, added a test that guards the trap.

**5. Test isolation was FICTIONAL → `pytest` wiped the real demo store.**
`conftest.py` set `DEMO_ALERT_STORE_FILE`, `NOTIFICATION_STORE_FILE`,
`DELIVERY_STORE_FILE` — **read by no backend code**. Those stores go through
`services/db.py` and resolved to `<cache>/store/docs_*.json` regardless. Tests that
call `reset_store()` therefore CLEARED the real demo alerts + notification log
(observed: stores emptied at 12:50 right after a pytest run). Only
`EMERGENCY_STORE_FILE` was ever honoured. Added `SAARTHI_STORE_DIR`, honoured by
`db._json_path`, which relocates the whole JSON store at once; conftest now sets it.
Proved with a sentinel: planted `{"sentinel": ...}` in the real store, ran the full
suite, sentinel survived.

**6. The watcher ticked at 300s but the demo lifecycle is 40s (alert_watcher.py).**
`ALERT_WATCH_INTERVAL=300` governed one loop that did both the local demo
advance/notify AND the network CAP check. The one-tap scenarios schedule pre-alert
at ~12s / ACTIVE at ~40s / ENDED at ~3min — and `demo_alerts.py` line 196 literally
says *"let the 10s lifecycle loop deliver it"*, a loop that did not exist. The
pre-alert push could arrive up to five minutes late, by which time the alert had
ended. Split the cadences: new `DEMO_TICK` (10s) runs the local pass, `interval`
(300s) still runs the network pass. `run_forever(interval, tick)`; both exposed on
`/api/push/status` (`demo_tick_seconds`).

**7. `sanitizeForTTS` declared THREE times in ChatPanel.jsx (lines 22, 73, 110).**
In an ES module top-level function declarations are lexical bindings, so duplicates
are a SyntaxError → `Identifier 'sanitizeForTTS' has already been declared` and the
whole ChatPanel module failed to parse in dev. Production build tolerated it, which
is why it hid. Kept the parameterised third definition, removed the other two.
Scanned all jsx/js: 0 files with duplicate top-level declarations remain.

### LLM brevity — measured, then fixed
Before: 1030 chars / 189 words (rain question), 813 / 132 (sea question).
Three causes:
1. `chat.py` prepended a guaranteed rain line whenever the literal text was
   absent — so the LLM's "**Yes**, it will rain tomorrow." was preceded by
   "Yes — rain likely tomorrow (22.0 mm)." **Two consecutive answers.** Extracted
   `_ensure_rain_lead()` (pure, tested) which now skips when the answer already
   commits to a yes/no in its first 220 chars.
2. `SYSTEM_RULES` told the model to "give practical actions" — but the server
   ALSO appends the authoritative advisory block, so advice appeared twice. The
   rules now forbid repeating practical advice, cap the answer at 120 words,
   require a ≤20-word opening that IS the answer, and ban preamble/closing
   summaries. `max_tokens` 400 → 240.
3. The advisory append itself (`answer = f"{answer}\n\n{advisory}"`) stays: it is
   the safety floor AND it is what gets spoken (ChatPanel speaks `r.answer`).
After: **433 chars / 66 words — 58% shorter**, one clean answer, yes-count 1.

### Onboarding tour was hijacking deep links

QA scripts must seed `localStorage['wgpt-onboarded']='1'` before load.
